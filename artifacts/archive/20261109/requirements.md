# T02 - 요구사항 정의서: 도시 관리 대시보드

## 배경 요약

관리자가 도시 데이터(도시명/국가/좌표/국가코드)를 조회·추가·수정·삭제할 수 있는 내부 전용
대시보드. 실제 백엔드 API는 개발 중이므로 `src/services/cityService.ts`는 목업으로 구현하되,
실제 API와 동일한 함수 시그니처(파라미터/반환 타입)를 유지해 이후 내부 구현만 교체 가능해야
한다. 인증/로그인은 이번 범위에서 제외한다.

## 2. 기능별 수용 기준 및 엣지 케이스

### F1. 도시 목록 조회

**수용 기준**
- 대시보드 진입 시 등록된 모든 도시를 목록(표 형태 권장)으로 표시한다.
- 각 행에는 최소한 도시명, 국가명, 국가코드, 위도, 경도가 표시된다.
- 목록이 비어 있으면 "등록된 도시가 없습니다" 등 빈 상태 안내를 표시한다.
- 목록 조회 중 로딩 상태를, 실패 시 에러 상태를 표시한다.

**엣지 케이스**
- 도시가 0개인 경우 (빈 상태 UI)
- 목록 조회 자체가 실패하는 경우 (재시도 유도 UI)
- 동일 국가에 여러 도시가 존재하는 경우 정상 표시되어야 함

### F2. 도시 검색

**수용 기준**
- 키워드 입력 시 도시명 기준으로 목록을 필터링한다 (API 계약상 `keyword` 파라미터 사용).
- 키워드가 비어 있으면 전체 목록을 표시한다.
- 검색 결과가 없으면 "검색 결과가 없습니다" 등 안내를 표시한다.

**엣지 케이스**
- 검색어에 공백만 있는 경우 (trim 후 빈 값으로 처리, 전체 목록 표시)
- 검색 결과 0건
- 대소문자/한글-영문 혼용 검색어 처리 방식은 "확인 필요" 참고

### F3. 도시 추가

**수용 기준**
- 관리자는 도시명, 국가명, 국가코드, 위도, 경도를 입력해 새 도시를 등록할 수 있다
  (`AddCityRequest` 계약: `cityName`, `countryName`, `lat`, `lng`, `countryCode`).
- 필수 필드(도시명, 국가명, 국가코드, 위도, 경도)가 모두 입력되어야 제출 가능하다.
- 등록 성공 시 목록에 즉시 반영되고, 성공 피드백(토스트 등)을 표시한다.
- 등록 실패 시 에러 메시지를 표시하고 입력값은 유지된다.

**엣지 케이스**
- **필수 필드 누락**: 하나라도 비어 있으면 제출을 막고 어떤 필드가 문제인지 표시한다.
- **위경도 범위 초과**: 위도는 -90~90, 경도는 -180~180 범위를 벗어나면 검증 오류를 표시하고
  제출을 막는다.
- **중복 도시명**: 동일 `cityName` + `countryName` 조합이 이미 존재하면 등록을 거부하고
  "이미 등록된 도시입니다" 등 명확한 오류를 표시한다. 유일성 판단 기준은 "도시명 + 국가명"
  조합으로 한다 (동명이인 도시가 다른 국가에 존재할 수 있으므로 도시명 단독으로는 판단하지
  않는다).
- **국가코드 형식**: ISO 3166-1 alpha-2(2자리 대문자) 형식을 벗어나면 검증 오류. 국기 매핑이
  실패할 경우 기본 아이콘/빈 국기로 대체하고 등록 자체는 막지 않는다.
- **숫자가 아닌 위경도 입력**: 숫자 파싱 실패 시 검증 오류.

### F4. 도시 수정

**수용 기준**
- 관리자는 기존 도시의 도시명/국가명/국가코드/위도/경도를 수정할 수 있다.
- 존재하는 `id`에 대해서만 수정이 가능하다.
- 수정 성공 시 목록에 즉시 반영되고 성공 피드백을 표시한다.

**엣지 케이스**
- **존재하지 않는 id 수정 시도**: "대상을 찾을 수 없습니다" 등 명확한 오류를 표시하고 목록을
  새로고침해 최신 상태를 반영한다.
- **필수 필드 누락 / 위경도 범위 초과**: F3과 동일한 검증 규칙 적용.
- **수정 후 중복 발생**: 수정 결과가 다른 기존 도시와 도시명+국가명이 겹치게 되는 경우
  F3과 동일하게 거부한다 (자기 자신과의 비교는 제외).
- **동시 수정/삭제 충돌**: 한 관리자가 수정하는 동안 다른 세션(또는 같은 세션의 중복 클릭)이
  동일 id를 삭제한 경우, 수정 요청은 "대상을 찾을 수 없음" 오류로 처리된다 (§3 참고).

### F5. 도시 삭제

**수용 기준**
- 관리자는 목록에서 도시를 선택해 삭제할 수 있다 (`DeleteCityRequest`: `{ cityId }`).
- 삭제 전 확인 다이얼로그를 표시해 실수 삭제를 방지한다.
- 삭제 성공 시 목록에서 즉시 제거되고 성공 피드백을 표시한다.

**엣지 케이스**
- **존재하지 않는 id 삭제 시도**: "대상을 찾을 수 없습니다" 오류를 표시하고 목록을 최신
  상태로 갱신한다 (이미 다른 세션에서 삭제된 경우 포함).
- **중복 삭제 요청(더블 클릭 등)**: 두 번째 요청은 "이미 삭제됨"으로 처리되어 오류가 나더라도
  최종 상태(목록에서 사라짐)는 일관되게 유지되어야 한다.

## 3. 동시 요청/중복 생성 유일성 보장 방식 (목업 서비스 레이어)

실제 DB가 없는 목업 환경이므로, 유일성 보장은 **서비스 레이어의 인메모리 저장소 접근을
직렬화**하는 방식으로 처리한다.

- 목업 데이터는 `src/mocks/` 내 모듈 스코프의 단일 배열(또는 Map)로 관리하고, 추가/수정/삭제
  요청은 이 저장소를 순차적으로 읽고-검증하고-쓰는 하나의 함수 내에서 원자적으로 처리한다
  (JS는 단일 스레드이므로 `async` 함수 내에서 지연(delay) 시뮬레이션 **이전에** 중복 검사와
  쓰기를 동기적으로 완료하면 경쟁 조건 없이 유일성이 보장된다).
- 구체적으로: 도시 추가 시 "도시명+국가명 중복 검사 → 통과 시 즉시 배열에 추가(동기 처리) →
  이후 인위적 지연/에러 시뮬레이션"의 순서를 지켜, 지연 중에 동시에 들어온 다른 요청이 같은
  중복 상태를 보고 통과하는 일이 없도록 한다.
- id 발급은 저장소 내 현재 최대 id + 1 또는 단조 증가 카운터로 처리해 충돌을 방지한다.
- 이 방식의 구체적 구현(락 형태, 지연 삽입 위치 등)은 backend-developer가 `api-spec.md`에서
  확정한다. 본 문서는 "동기적 검증+쓰기 후 비동기 지연" 원칙만 요구사항으로 명시한다.

## 4. 비기능 요구사항

- **성능**: 낮은 우선순위. 목업 데이터 규모가 작을 것으로 예상되므로 별도 가상화/페이지네이션
  성능 최적화는 요구하지 않는다.
- **접근성**: 기본 수준 고려. 폼 입력에 label 연결, 버튼에 명확한 텍스트/aria-label, 키보드로
  기본 조작(탭 이동, 폼 제출, 다이얼로그 닫기)이 가능해야 한다. WCAG 준수 수준의 정밀 검증은
  범위 밖으로 한다.
- **반응형**: 관리자 데스크톱 사용을 우선하되 완전히 배제하지는 않는다. 구체적인 모바일
  브레이크포인트 지원 범위는 "확인 필요" 참고.
- **보안/인증**: 이번 범위 밖. 내부 전용 도구로 가정하며 로그인/권한 체크는 구현하지 않는다.
- **국제화**: 별도 요구 없음(한국어 UI 기준).

## 5. 확인 필요 (project-manager 제안 기본값 포함)

이번 실행은 T02 완료 후 사용자 확인 게이트가 생략되어, 아래 항목은 진행을 막지 않고 제안
기본값과 함께 다음 단계(designer, backend-developer)에 전달한다.

1. **도시 수정(update) API 계약 미확정**
   원본 저장소(`17th-team1-client`)에 수정 API가 존재하지 않는다. `AddCityRequest`와 대칭되는
   형태로 backend-developer가 추론해 `api-spec.md`에 확정해야 한다.
   - 제안 기본값: `PUT /api/v1/cities/{cityId}`, 요청 바디는 `AddCityRequest`와 동일한 필드
     구성(`cityName`, `countryName`, `lat`, `lng`, `countryCode`), 응답은 `AddCityResponse`와
     동일한 형태(`{ status, data: CityApiData }`).

2. **목업 에러/지연 시뮬레이션 정책 미정**
   실패율, 지연 시간, 어떤 케이스에서 에러를 던질지가 명시되지 않았다.
   - 제안 기본값:
     - 지연: 모든 요청에 300~800ms 사이 랜덤 지연을 적용해 실제 네트워크 호출처럼 보이게 한다.
     - 실패율: 조회(F1/F2)는 실패 시뮬레이션 없음(항상 성공). 추가/수정/삭제(F3/F4/F5)는
       기본적으로 성공하되, 명시적 비즈니스 규칙 위반(중복 도시명, 존재하지 않는 id)에 대해서만
       결정적으로(랜덤 아님) 오류를 반환한다. 순수 랜덤 서버 오류(예: 5% 확률의 500 에러)는
       기본값에 포함하지 않는다 — 필요 시 QA/개발 단계에서 별도 플래그로 켤 수 있게 한다.
     - 이 기본값은 backend-developer/QA가 최종 확정한다.

3. **목록 UX 상세(정렬/필터/페이지 크기) 미정**
   정렬 기준, 필터 옵션, 페이지 크기가 명시되지 않았다.
   - 제안 기본값: 등록 순(id 오름차순) 정렬, 별도 필터 없이 검색(F2)만 제공, 페이지네이션 없이
     전체 목록을 한 화면에 스크롤로 표시(목업 데이터 규모가 작다는 전제, §4 성능 참고). 데이터
     규모가 커질 경우를 대비해 designer는 추후 페이지네이션을 추가하기 쉬운 레이아웃을 고려할
     것을 권장한다.

4. **반응형 지원 범위 (비기능 요구사항 관련, 판단 애매)**
   관리자 데스크톱 우선이되 완전히 배제하지 않는다는 지침은 있으나, 구체적으로 어느
   브레이크포인트까지 지원할지 불명확하다.
   - 제안 기본값: 데스크톱(1024px 이상)을 기준으로 설계하고, 태블릿(768px~1023px)까지는
     레이아웃이 깨지지 않는 수준으로 대응한다. 모바일(767px 이하) 전용 최적화는 이번 범위에서
     제외하고 designer 판단에 맡긴다.

5. **검색 시 대소문자/한글-영문 혼용 처리 방식 미정**
   - 제안 기본값: 대소문자 구분 없이(case-insensitive) 부분 문자열 포함 여부로 검색한다.

6. **인증 확장 여지**
   이번 범위에서는 인증을 고려하지 않으나, 추후 인증이 추가될 경우를 대비해 API 클라이언트
   레이어(예: `apiClient.ts` 유사 구조)를 인증 헤더 삽입이 쉬운 형태로 설계할 것을 권장한다.
   이는 요구사항이 아닌 designer/backend-developer를 위한 참고 권고 사항이다.
