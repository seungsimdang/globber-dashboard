# T02 - 요구사항 정의: 실제 도시 API 연동

입력: `artifacts/task-team/00-input.md`. 이 문서는 요구사항만 정의하며 설계·구현 방식은 정하지 않는다.
"확인됨"은 00-input.md가 서버 호출로 확인했다고 적은 사실이고, "코드 확인"은 이 저장소 코드를 직접 읽은 사실이다. 그 외는 제안 또는 미확인이다.

## 1. 목적과 범위

목업 서비스 레이어(`src/services/cityService.ts` + `src/mocks/*`)를 실제 Globber 도시 API 호출로 교체한다. 브라우저는 Next 서버만 호출하고, Next 서버가 실제 API와 토큰을 다룬다.

> 2차 주석: 이 문서 본문은 상류 서버가 개발 서버 하나(`CITY_API_BASE_URL` 하나)라는 전제로 쓰였다. 2차에서 운영·개발 두 서버를 탭으로 전환해 관리하도록 바뀌었으며, 충돌하는 문장은 아래 "2차: 운영·개발 서버 분리" 절이 우선한다.

### 확정 사항 (00-input.md "사용자 결정", 변경하지 않음)

- 토큰은 dev `/dev/test-login`을 Next 서버가 호출해 받는다. 테스트 이메일은 서버 환경 변수, 토큰은 서버에만 보관, 401이면 재발급한다. 기존 단일 계정 로그인(`src/lib/session.ts`)은 유지한다.
- 호출 경로는 브라우저 -> Next 서버 -> 실제 API다. 토큰과 API 주소는 브라우저에 노출하지 않는다.
- 브랜치는 `feature/real-city-api`(main 분기). 관리자 인증 요청 문서는 만들지 않는다.
- 데이터를 바꾸는 요청(POST/PUT/DELETE 성공 경로)은 사용자 승인 없이 실제 서버에 보내지 않는다.

## 2. 현재 상태 (코드 확인)

- `cityService.ts`는 5개 함수(`getCities`, `searchCities`, `addCity`, `updateCity`, `deleteCity`)를 내보내고 `City`(id가 string, `flag` 포함)를 반환한다. 입력 검증(필수값, 위경도, 이름 100자, `^[A-Z]{2}$`)과 중복·없는 id 에러를 서비스 안에서 던진다.
- `useCities`는 keyword가 비면 `getCities`, 있으면 `searchCities`를 호출한다.
- `CityFormModal.tsx`는 국가코드를 영문 2자로 검증한다(오류 문구 "국가코드는 영문 2자(예: KR)로 입력해주세요").
- `countryFlagMapping.ts`는 alpha-2 키(`KR` 등) 기준이다. `CityListTable`은 `city.flag`와 `city.countryCode`를 표시한다.
- `src/types/city.ts`의 `CityApiResponse`(`cityResponseList`)는 `/favorites` 기준이고, 실제 `/cities/all`과 `/cities?keyword=`의 응답 키는 00-input.md상 검색이 `data.cities[]`다. `/cities/all` 응답 형태는 00-input.md에 적혀 있지 않다(B-7에서 확인됨).
- `src/lib/apiClient.ts`는 없다. `.env.example`에는 API 관련 변수가 없다.

### F-01 서버 경유 계층

- 브라우저는 Next 서버의 자체 경로만 호출한다. 실제 API 주소(`54.180.101.234:8080` 등)와 토큰은 브라우저 번들·응답·네트워크 요청 어디에도 나타나지 않는다.
- 클라이언트의 HTTP 호출은 `src/lib/apiClient.ts`를 통한다(`nextjs.md` 5번).
- 실제 API 주소는 서버 환경 변수로 관리하고 코드에 하드코딩하지 않는다. (2차 주석: 주소는 운영·개발 각각 별도 환경 변수가 된다. 2차 절 참조)
- 서버 경유 경로는 기존 세션 쿠키(`globber_session`)로 보호한다. 세션이 없으면 실제 API를 호출하지 않고 거부한다(`nextjs.md` 3번, Proxy만 믿지 않고 핸들러도 검증).
- 서비스 함수 5개의 시그니처와 반환 타입(`City`, `City[]`, `void`)은 가능한 한 유지해 훅·컴포넌트 변경을 최소화한다(`react-query.md` 1번). 시그니처를 바꿔야 하면 사유를 T03에 명시한다.
- 수용 기준
  - 브라우저 개발자 도구 네트워크 탭에서 실제 API 호스트로 가는 요청이 없다.
  - 번들 검색 시 실제 API 주소·토큰·테스트 이메일이 없다.
  - 로그인하지 않은 상태로 서버 경유 경로를 호출하면 401 또는 로그인 리다이렉트로 거부되고 실제 API 호출이 발생하지 않는다.
- Edge case: 실제 API가 보내는 `{status:"fail", data:"메시지"}`를 브라우저에 어떤 형태로 전달할지(상태 코드 유지, 메시지 문자열 유지)는 설계 단계 결정이다. 요구사항은 "서버 메시지가 사용자에게 의미 있게 표시된다"까지만 정한다.

### F-02 전체 목록 조회

- 로그인 후 `/cities` 진입 시 `GET /api/v1/cities/all`의 도시를 목록에 표시한다. 토큰 없이 200이 확인됐으나(조회·검색), 서버 경유 계층에서 토큰을 붙일지는 설계 결정이다.
- 응답은 `CityApiData` -> `City` 변환(id를 string으로, 국기 계산)을 기존 `transformApiDataToCity`와 동일한 결과로 만든다.
- 수용 기준
  - 실제 응답 3,791개가 누락·중복 없이 로드된다(건수 일치). (2차 주석: 3,791개는 개발 서버 건수다. 운영은 4,204개로 확인됐다. 2차 절 참조)
  - 한글 도시명·국가명(예: `두바이`, `아랍에미리트`)이 깨지지 않는다.
  - 로딩 중에는 로딩 상태, 실패 시 오류 메시지와 재시도 버튼이 보인다(기존 UI 유지).
- Edge case
  - 3,791개를 한 번에 렌더링할 때의 성능. 현재 `CityListTable`에 페이지네이션이 없다(코드 확인: 전체 `cities`를 그대로 전달). 렌더링 지연이 체감되면 부분 렌더링이 필요한지 판단해야 하며, 이는 "확인 필요" B-1에 둔다.
  - `Cache-Control: max-age=86400, public`과 ETag(확인됨). 도시 추가·수정·삭제 직후 목록이 캐시 때문에 갱신되지 않으면 안 된다. 쓰기 후 목록이 즉시 최신 상태여야 한다.
  - 응답이 빈 배열이면 기존 빈 상태 UI를 표시한다.

### F-03 검색

- 검색어(trim 후)가 있으면 실제 검색 API(`GET /api/v1/cities?keyword=`)의 결과를 표시한다. 결과는 유사도+인기순 최대 20개다(확인됨).
- 위 동작은 제안 기본값이며 전체 목록 클라이언트 필터링과의 선택은 "확인 필요" B-1이다.
- 수용 기준
  - 검색 결과가 20개로 잘릴 수 있음을 사용자가 알 수 있다 (결과 개수가 20이면 "상위 20개만 표시" 같은 안내. 목록의 일부만 보여주는 UI이므로 전체 개수와의 관계를 메시지로 표현한다).
  - 결과 순서는 서버가 준 순서(유사도순)를 유지한다. 클라이언트가 임의로 재정렬하지 않는다.
  - 결과가 없으면 기존 "검색 결과 없음" UI를 표시한다.
- Edge case
  - 빈 검색어·공백: 서버가 400(`검색어를 입력해 주세요.`)을 반환한다(확인됨). 클라이언트는 trim 후 비어 있으면 검색 API를 호출하지 않고 전체 목록으로 돌아간다(기존 `useCities` 동작과 동일).
  - 한글·특수문자·공백이 섞인 검색어가 URL 인코딩되어 전달된다.
  - 검색어를 연속 입력할 때 이전 요청 결과가 나중에 도착해 화면을 덮어쓰지 않는다.
  - 검색 API가 인기순 가중치를 쓰므로 대시보드에서 "정확히 일치하는 도시"가 첫 줄에 오지 않을 수 있다. 이 동작 차이는 사용자에게 알려야 하는 사실이다(미확인 정렬 로직은 추정하지 않는다).

### F-04 서버 측 토큰 관리

- Next 서버가 `POST /dev/test-login?email=`을 호출해 accessToken(과 refreshToken)을 받고 서버에만 보관한다. 이메일은 서버 환경 변수로 받는다.
- 쓰기 요청(POST/PUT/DELETE)에 토큰을 붙인다. 실제 API가 401을 반환하면 토큰을 재발급해 원래 요청을 한 번 재시도한다. 재시도도 401이면 실패로 처리하고 무한 재시도하지 않는다.
- 수용 기준
  - 토큰이 없거나 만료된 상태에서 첫 쓰기 요청이 사용자 개입 없이 성공한다(재발급 후 재시도).
  - 동시에 여러 요청이 401을 만나도 재발급 요청이 요청 수만큼 폭주하지 않는다(재발급 중복 방지 방식은 설계 결정).
  - 토큰 값이 로그·응답·에러 메시지에 노출되지 않는다.
  - 테스트 이메일 환경 변수가 없으면 쓰기 요청이 명확한 서버 설정 오류로 실패하고 조회·검색은 영향이 없다(조회가 토큰 없이 가능한 것은 확인됨).
  - `accessToken` 값에 `Bearer ` 접두사가 포함되는지 불명확하므로(확인 필요 A-2) 어느 경우든 올바른 `Authorization` 헤더가 만들어져야 한다.
- 제약: 토큰 보관 위치와 수명은 서버 프로세스 범위다. 서버리스·다중 인스턴스에서 보관소가 공유되지 않으면 재발급이 잦아질 수 있다(배포 환경 미확인, 확인 필요 B-8).
- 배포 관련: 새 서버 환경 변수(API 주소, 테스트 이메일)가 필요하다. 변수 이름은 설계 단계에서 정하고 `.env.example`과 배포 환경(Vercel 등) 설정 대상으로 문서화한다. 이 요구사항에 크론은 없다.
- 운영 서버 제약: test-login은 "[dev/local 환경만]"이다(확인됨). 운영(`https://globber.world/api`)에서는 이 방식으로 쓰기가 동작하지 않는다. 사용자가 운영 연동을 요청하지 않았으므로 이번 범위는 dev 서버 대상이다(확인 필요 A-3). (2차 주석: 2차에서 운영 조회가 추가됐다. 토큰은 여전히 개발 서버 전용이고 운영 쓰기는 비활성이다. 2차 절 참조)

### F-05 도시 추가

- 입력 5개(cityName, countryName, lat -90~90, lng -180~180, countryCode alpha-3 `^[A-Z]{3}$`)를 `POST /api/v1/cities`로 보내고, 응답 `data`(`CityResponse`)를 `City`로 변환해 반환한다.
- 유일성(동시 요청/중복 생성): 목업은 서비스에서 중복(도시명+국가명)을 막았다. 실제 API는 중복 시 응답이 확인되지 않았다(확인 필요 A-5). 요구사항은 "중복 생성이 실제 서버에서 거부되거나 클라이언트가 안내"로 두고, 유일성 보장은 서버(실제 API) 책임이라고 가정한다. 이 가정은 미확인이므로 "확인 필요"에 남긴다.
- 수용 기준
  - 추가 성공 시 목록이 갱신된다(`invalidateQueries`).
  - 필수값 누락, 위경도 범위 초과, alpha-3 형식 위반은 클라이언트 폼에서 먼저 막고, 서버 400이 와도 서버 메시지가 표시된다.
  - 추가 중 버튼이 비활성화되어 이중 제출이 되지 않는다.
- Edge case: 실제 서버에 쓰는 요청이므로 검증은 승인 없이 성공 경로를 보내지 않는다(테스트는 모킹된 `fetch`/핸들러로 한다). 이름 길이 100자 제한은 실제 스펙에 없다(00-input.md에 길이 제한 기재 없음) - 유지할지는 확인 필요 B-5.

### F-06 도시 수정

- `PUT /api/v1/cities/{cityId}`에 `CityRequest` 전체 5개 필드를 보낸다. 수정 계약은 이제 실제 스펙(확인됨)으로 확정되며, 기존에 "추가와 대칭으로 제안"했던 `UpdateCityRequest`는 실제 스펙과 대조해 일치함을 확인하는 것이 완료 기준이다(`CityRequest` 필수 5개 필드와 `UpdateCityRequest`가 동일 구조인 것은 코드·00-input.md 대조로 확인).
- 수용 기준
  - 수정 모달은 대상 도시 `id`만 받아 초기값을 세팅한다(`react-query.md` 7번). 기존 동작 유지.
  - 성공 시 목록 갱신, 실패 시 서버 메시지 표시.
  - 서버가 없는 id를 어떻게 응답하는지 미확인(확인 필요 A-5)이므로, 응답이 4xx이면 "대상을 찾을 수 없습니다" 계열 메시지 표시 후 목록 재조회를 한다.
- Edge case: 검색 결과 20개 중 항목을 수정했을 때 검색 결과 순서가 바뀔 수 있다. 수정 후 목록은 현재 keyword 기준으로 재조회한다.

### F-07 도시 삭제

- `DELETE /api/v1/cities/{cityId}`. 응답은 삭제된 `CityResponse`지만 서비스 반환 타입은 기존대로 `void`를 유지한다(제안).
- 수용 기준
  - 삭제 확인 다이얼로그 후 호출하고, 성공 시 목록 갱신, 실패 시 서버 메시지 표시.
  - 이미 삭제된 id를 다시 삭제하면 서버 응답(미확인)에 맞는 메시지를 표시하고 목록을 재조회한다.
  - 삭제 요청 중 이중 클릭이 막힌다.

### F-08 countryCode alpha-3 전환

영향 범위 (코드 확인 + 00-input.md):

| 대상 | 현재 | 요구사항 |
| --- | --- | --- |
| `CityFormModal.tsx` 검증·오류 문구 | 영문 2자, "예: KR" | 영문 대문자 3자(`^[A-Z]{3}$`), 문구 예시는 실데이터 기준(`KOR` 등. 예시 값은 실제 존재하는 코드로 한다) |

| `countryFlagMapping.ts` | alpha-2 키로 국기 이모지 매핑 | alpha-3 입력에서 국기가 표시되어야 한다. alpha-3 -> alpha-2 변환 또는 alpha-3 키 매핑 중 선택은 설계 결정 |

- 수용 기준
  - 실제 응답의 alpha-3 값(예: `ARE`)을 가진 도시에서 국기가 표시된다.
  - 매핑에 없는 alpha-3 코드(예: 소수 영토, 신규 국가)는 기존처럼 폴백 표시가 나오고 목록이 깨지지 않는다. 폴백 모양은 현재 `getCountryFlag`의 미매핑 동작을 따른다(상세는 코드 확인 후 T03).
  - alpha-2 2자 입력은 폼에서 오류가 된다.
  - 3,791개 도시 전체에 대해 매핑이 얼마나 비는지는 확인되지 않았다. 실데이터의 고유 countryCode 수와 현재 매핑 수를 비교하는 것은 T03/T05 사전 확인 항목이다(확인 필요 B-4).
- Edge case: 사용자가 소문자로 입력하면 기존처럼 trim 후 대문자 변환한다. 입력 기준 UX는 유지한다.

### F-09 에러·로딩 UX

- 네트워크 실패(서버 도달 불가, 타임아웃), 4xx(400 검증, 401 재발급 실패), 5xx를 구분해 사용자에게 메시지를 표시한다. 서버가 준 메시지(`data` 문자열)가 있으면 우선 표시한다.
- 목업 지연·에러 시뮬레이션(`mockDelay`)은 사라진다. 로딩/에러 UI는 실제 네트워크로 검증한다(`react-query.md` 5번의 목업 전제가 바뀐다 - 규칙 문서 갱신 필요 여부는 확인 필요 B-2과 함께 판단).
- 수용 기준
  - 네트워크 실패 시 목록 영역에 오류와 재시도가 표시되고, 쓰기 실패 시 모달이 열린 채로 오류가 표시되어 입력값이 보존된다.
  - 401 재발급까지 실패하면 "서버 인증에 실패했습니다" 계열의 메시지를 표시하고 토큰 값은 노출하지 않는다.
  - 대시보드 로그인 세션 만료와 실제 API 토큰 만료를 사용자가 혼동하지 않는다(세션 만료는 로그인 화면으로, API 인증 실패는 오류 메시지).

## 4. 비기능 요구사항

- 보안: 토큰·API 주소·테스트 이메일은 서버에만 존재한다. 서버 경유 경로는 로그인 세션 검증 필수. 실제 API 응답 오류 본문을 그대로 브라우저에 흘리지 않고, 사용자에게 필요한 메시지 문자열만 전달한다.
- 성능: 목록 응답이 3,791개다. 초기 로딩 후 렌더링이 사용 가능한 시간 안에 끝나야 한다. 구체 수치 목표는 사용자가 정하지 않았으므로 정하지 않는다(확인 필요 B-1에서 판단).
- 캐시: 서버 응답이 `max-age=86400, public`이다(확인됨). 쓰기 직후 목록이 오래된 값을 보이지 않아야 한다.
- 접근성: 기존 폼·테이블·다이얼로그의 접근성 속성을 유지한다. 새 안내 문구(검색 20개 제한)는 스크린리더에도 읽힌다.
- 호환: 데스크톱 우선(최소 1024px), 기존 디자인·애니메이션 유지(`project.md`, 공통 작업 제약).
- 테스트: 실제 서버에 쓰기 요청을 보내지 않는다. 자동 테스트는 모킹된 네트워크로 하며, 수동 쓰기 검증은 사용자 승인 후에만 한다.

| --- | --- |
| 화면 분리 | 한 화면(`/cities`) 안의 탭으로 운영·개발 전환. 주소 분리 없음 |
| 운영 쓰기 | 운영 탭의 추가·수정·삭제 버튼은 비활성+안내 문구 (백엔드가 쓰기용 인증 수단을 줄 때까지) |
| 개발 서버 | IP 서버(`http://54.180.101.234:8080` 계열). 실제 값은 문서·코드에 적지 않고 환경 변수로만 둔다 |
| 주소 관리 | 운영·개발 주소를 각각 환경 변수로 관리. 코드 수정 없이 변경 가능 |
| 작업 위치 | PR #19(`feature/real-city-api`)에 이어서 커밋 |

### 현재 상태 (코드 확인)

- 상류 주소는 환경 변수 `CITY_API_BASE_URL` 하나다(`cityApiToken.ts`의 `getCityApiBaseUrl`). 목록 경로는 `route.ts`에서 `/api/v1/cities/all`로 고정, 토큰 발급은 `{base}/dev/test-login?email=`이다.
- 운영 기준 주소는 끝에 `/api`가 붙는다(확인됨: `https://globber.world/api/v1/cities/all`은 404). 즉 운영과 개발(IP)은 "기준 주소 + 도시 경로" 조합이 서로 다르다. 경로를 어떻게 맞출지는 설계 결정이다.
- 토큰(`accessToken`, `inflight`)은 모듈 변수 하나이며 서버 구분이 없다.
- `useCities`의 queryKey는 `queryKeys.cities.list` 하나이고 `getCities`는 서버 인자를 받지 않는다. 쓰기 훅은 이 키를 invalidate한다.
- 확인됨: 토큰 발급은 개발(IP)에서만 도달한다. 개발(도메인)은 `/dev/test-login`에 닿지 않고, 운영에는 없다. 따라서 쓰기는 개발(IP)에서만 가능하다.

## 2-2. 기능 분해와 우선순위

P0 = 없으면 분리 불가, P1 = 완료 조건, P2 = 보완.

| ID | 기능 | 우선순위 |
| --- | --- | --- |
| S-01 | 운영·개발 서버 주소를 각각 환경 변수로 관리 | P0 |
| S-02 | 서버 경유 계층이 요청마다 대상 서버(운영/개발)를 구분해 호출 | P0 |
| S-03 | `/cities` 화면의 운영·개발 탭 전환 | P0 |
| S-04 | 탭(서버)별 조회 캐시 분리와 쓰기 후 갱신 범위 | P0 |
| S-05 | 운영 쓰기 차단 (버튼 비활성+안내 + 서버 거부) | P0 |
| S-06 | 토큰은 개발 서버 전용 | P0 |
| S-07 | 현재 서버 오인 방지 표시 | P1 |
| S-08 | 환경 변수 누락·오류 시 동작 | P1 |
| S-09 | 문서·테스트 갱신 (`.env.example`, `city-api-reference.md`, `project.md` 백엔드 설명, 테스트) | P2 |

### S-01 서버 주소 환경 변수

- 운영·개발 상류 주소를 각각 별도 서버 환경 변수로 받는다. 변수 이름은 설계 단계에서 정하고 `.env.example`에 가짜 값(placeholder)으로만 적는다. 실제 IP·도메인은 문서·코드·테스트 픽스처에 적지 않는다.
- 두 주소는 브라우저 번들·응답·네트워크 요청에 나타나지 않는다(1차 F-01 유지).
- 수용 기준
  - 환경 변수만 바꿔 재시작/재배포하면 코드 수정 없이 두 서버의 대상이 바뀐다.
  - 기존 `CITY_API_BASE_URL`을 어떻게 다룰지(이름 변경, 개발용으로 계승, 제거)가 정해지고 `.env.example`·배포 설정 절차에 반영된다(사용자 결정 U-1).
- Edge case
  - 후행 슬래시, 운영 주소의 `/api` 접두 유무 차이는 설정 값 실수로 이어지기 쉽다. 형식 기준(어디까지 환경 변수에 포함하는지)을 문서화한다.

### S-02 서버 지정 호출

- 모든 `/api/cities*` 요청이 대상 서버를 구분해서 도착한다(전달 방식은 설계 결정). 대상이 없거나 알 수 없는 값이면 400으로 거부하고 상류를 호출하지 않는다. 임의 URL·호스트를 클라이언트가 지정할 수 없고 허용 목록은 운영·개발 두 값뿐이다(SSRF 방지).
- 수용 기준
  - 운영 지정 시 운영 주소, 개발 지정 시 개발 주소로만 호출된다(모킹 fetch로 URL 검증).
  - 세션이 없으면 대상과 무관하게 상류 호출 없이 거부된다(1차 F-01 유지).
  - 대상 누락 시 기본값을 몰래 개발로 두지 않는다(기본값 정책은 U-2에서 확정, 서버 쪽은 명시 필수가 안전한 방향이라는 것이 제안).

### S-03 탭 전환 UI

- `/cities`에 "운영" "개발" 두 탭을 둔다. 한 번에 한 서버의 목록을 본다. 접근성: 탭 역할과 선택 상태가 스크린리더에 전달되고 키보드로 전환된다. 기존 디자인·1024px 최소 너비를 유지한다. Radix UI primitive 사용 가능 여부는 `project.md` 규칙대로 구현 단계에서 먼저 확인한다.
- 수용 기준
  - 탭 클릭 시 해당 서버의 목록·건수가 표시된다.
  - 새로고침/최초 진입 시 기본으로 선택되는 탭이 정해져 있다(U-2). 주소를 나누지 않는 결정이므로 URL 경로는 `/cities` 하나다. 선택을 쿼리스트링 등에 반영할지는 U-2에서 함께 정한다.
  - 한 탭의 로딩·오류가 다른 탭 표시에 영향을 주지 않는다.
- Edge case
  - 탭 전환 시 검색어: 전환 시 유지할지 초기화할지는 사용자 선호이므로 U-3에서 결정한다. 어느 쪽이든 입력창 표시값과 실제 필터 값이 어긋나면 안 된다.
  - 탭 전환 시 열린 모달(추가/수정/삭제 확인): 대상 서버가 바뀌면 다른 서버의 id로 요청이 가는 사고가 난다. 제안 기본값은 "모달이 열려 있는 동안 탭 전환 불가(또는 전환 시 모달을 닫고 입력 폐기)"이며 U-3에서 확정한다. 어느 경우든 모달의 쓰기 요청은 모달을 연 시점의 서버로 가거나 요청 자체가 막혀야 하고, 섞이지 않는다.
  - 진행 중인 쓰기 요청이 있을 때 탭을 전환해도 요청은 원래 서버로 완료되고 결과(성공/실패 메시지)가 현재 탭 화면에 잘못 표시되지 않는다.
  - 탭 전환 중 이전 서버의 응답이 늦게 도착해도 현재 탭 목록을 덮어쓰지 않는다.

### S-04 조회 캐시 분리

- 목록 캐시는 서버별로 분리한다. 운영 목록과 개발 목록이 같은 캐시 키를 공유하지 않는다(4,204개와 3,791개가 뒤섞이면 안 된다).
- 수용 기준
  - 운영 탭 -> 개발 탭 -> 운영 탭 전환 시 각 탭의 건수가 항상 해당 서버의 건수와 일치한다.
  - 개발 탭에서 쓰기 성공 후 갱신되는 대상은 개발 목록이다. 운영 캐시는 불필요하게 무효화하지 않는다.
  - 검색(클라이언트 필터링, 1차 B-1)은 현재 탭 캐시를 대상으로 한다. 전체 건수와 필터 결과 건수 표시는 현재 탭 기준이다.
  - 중복 도시 사전 검사(1차 B-6)는 현재 탭(쓰기가 가능한 개발)의 전체 목록을 기준으로 한다.
- Edge case
  - 두 서버 데이터가 서로 다르므로(건수 차이 확인됨) 운영에서 보던 도시 id를 개발 요청에 쓰는 일이 없어야 한다. id는 서버 간에 같은 의미라고 가정하지 않는다(확인 필요 C-2).
  - 한쪽 서버 장애 시 다른 서버 탭은 정상 동작한다.

### S-05 운영 쓰기 차단

- 운영 탭에서 추가·수정·삭제 버튼은 비활성이며 이유를 설명하는 안내 문구가 보인다(예: 운영 서버는 현재 조회만 가능). 문구는 `src/utils/cityErrorMessage.ts`를 통해 통일한다(`project-structure.md` 4번).
- 버튼 비활성은 UI 보호일 뿐이며 서버(Route Handler)도 운영 대상 POST/PUT/DELETE를 거부한다. 거부는 상류 호출·토큰 발급 이전에 일어난다.
- 수용 기준
  - 운영 탭에서 세 쓰기 버튼이 비활성이고 안내 문구가 표시된다. 키보드/스크린리더로도 비활성 사유를 알 수 있다.
  - 세션이 있는 상태에서 운영 대상으로 `/api/cities` POST, `/api/cities/{id}` PUT·DELETE를 직접 호출하면 4xx(403 또는 400 계열, 상태 코드는 설계 결정)로 거부되고 상류 fetch가 0회, 토큰 발급 요청도 0회다.
  - 개발 탭에서는 1차의 쓰기 동작이 그대로 유지된다.
  - 이미 열려 있던 쓰기 UI(모달 등)가 운영 탭 전환 후에도 남아 쓰기를 보낼 수 없다(S-03 edge case와 연계).
- 운영 쓰기 허용은 백엔드가 인증 수단을 제공한 뒤 별도 사이클에서 한다. 이번 2차에서 허용 경로를 열어 두지 않는다(환경 변수 플래그 등으로 풀 수 있게 만드는 것도 요청되지 않았으므로 범위 밖).

### S-06 토큰은 개발 서버 전용

- test-login 토큰 발급·보관·`Authorization` 부착은 개발 서버 호출에만 쓴다. 운영 서버 요청(조회 포함)에는 토큰도 이메일도 보내지 않는다. 운영 서버로 test-login을 호출하지 않는다(404 확인됨).
- 수용 기준
  - 운영 조회 시 상류 요청에 `Authorization` 헤더가 없고 test-login 호출이 없다.
  - 토큰 발급 URL은 개발 서버 주소에서만 만들어진다. 개발 토큰이 운영 요청에 재사용되지 않는다(토큰 변수가 서버를 가리지 않는 현재 구조에서 생기는 오용 방지).
  - 개발 서버의 401 재발급+1회 재시도(1차 F-04)는 그대로 유지된다.
  - 토큰 값·이메일·주소는 로그·응답·에러 메시지에 노출되지 않는다(1차 유지).
- 확인 필요: 개발(IP) 서버의 쓰기 동작(토큰 만료 시간, `Bearer` 접두사, 일반 회원 토큰의 쓰기 권한, 중복/없는 id 응답)은 1차에서 이월된 미확인 항목이다(00-input.md 2차 확인 필요 2번). 2차에서도 추측으로 채우지 않는다.

### S-07 현재 서버 오인 방지

- 사용자가 지금 보고 있는 데이터가 운영인지 개발인지 항상 구분할 수 있어야 한다. 쓰기가 엉뚱한 서버로 가는 사고(운영이라고 생각하고 개발을 고치거나 반대)를 막는 것이 목적이다.
- 수용 기준
  - 선택된 탭이 시각적으로 명확하다(색 외에 텍스트 라벨 병행).
  - 목록 영역(제목/건수/빈 상태/오류/재시도 문구)에 현재 서버 이름이 드러난다. 예: "운영 서버 도시 4,204개"가 아니라 건수만 나오는 문구는 허용되지 않는다. 구체 문구는 디자인 단계.
  - 쓰기 모달(추가/수정)·삭제 확인 다이얼로그에 대상 서버 이름이 표시된다.
  - 쓰기 성공/실패 메시지에 어느 서버에 대한 것인지 식별 가능하다.
- Edge case: 개발(IP)과 개발(도메인)이 같은 서버인지 미확인(00-input.md 확인 필요 1번). 화면 라벨은 "개발"로 두며 IP/도메인 구분을 사용자에게 노출하지 않는다.

### S-08 환경 변수 누락·오류 동작

- 한쪽 서버 환경 변수가 없어도 다른 서버는 영향받지 않는다. 누락된 서버를 지정한 요청은 서버 설정 오류(500, 기존 `UpstreamConfigError` 경로와 같은 방식)로 실패하고 해당 탭에 "서버 설정 오류" 메시지와 재시도가 보인다. 주소·변수 이름·토큰은 메시지에 노출하지 않는다는 1차 원칙을 유지한다(코드 확인: 현재 메시지는 "도시 API 주소가 설정되지 않았습니다"로 값은 노출하지 않음. 변수 이름을 사용자 메시지에 넣을지는 설계 결정).
- 수용 기준
  - 운영 주소만 없을 때: 개발 탭 정상, 운영 탭 설정 오류.
  - 개발 주소만 없을 때: 운영 탭 조회 정상, 개발 탭 설정 오류, 개발 쓰기 불가.
  - 테스트 이메일(`CITY_API_TEST_EMAIL`)만 없을 때: 조회(양쪽)는 정상, 개발 쓰기만 설정 오류(1차 F-04 유지).
  - 둘 다 없을 때: 두 탭 모두 설정 오류. 앱 기동이 크래시하지 않는다.
  - 주소 형식이 잘못됐을 때(빈 문자열, 비 URL): 설정 오류 또는 연결 실패로 일관되게 처리하고 상류 호출로 새어나가지 않는다.
- 배포: 환경 변수 이름이 늘거나 바뀌므로 Vercel 등 배포 환경 재설정이 필요하다. 변경된 변수 목록과 절차를 `.env.example`과 PR 설명에 적는다(구체 설정 자체는 사용자/배포 담당 작업이며 이 에이전트가 값을 적지 않는다). 이 기능은 크론이나 능동 트리거가 없는 요청 기반 동작이다.

### S-09 문서·테스트

- `.env.example`, `src/docs/city-api-reference.md`(운영·개발 두 기준 주소와 경로 차이), `docs/agent-rules/project.md`(백엔드 설명이 dev 서버 기준이므로 운영·개발 병행으로 갱신)를 갱신한다. 실제 주소·이메일 값은 적지 않는다(변수 이름만).
- 자동 테스트는 모킹된 네트워크로 한다. 실제 서버에 쓰기 요청을 보내지 않는다(1차 유지). 운영 서버에는 조회 외 요청을 어떤 경우에도 보내지 않는다.

## 2-3. 전체 수용 기준 (완료 기준)

1. `/cities`에서 운영·개발 탭으로 각 서버 목록을 조회하며, 각 탭의 건수가 서버 실제 건수와 일치한다(조회 전용 요청으로 검증 가능: 운영 4,204, 개발 3,791은 2026-11-09 확인값이며 데이터가 바뀌면 달라질 수 있음).
2. 운영 탭에서 쓰기 버튼이 비활성+안내이고, 운영 대상 쓰기 요청은 서버에서도 상류 호출 0회로 거부된다(모킹 테스트).
3. 개발 탭의 추가·수정·삭제와 401 재발급 동작은 1차와 같다.
4. 운영 요청에는 토큰·테스트 이메일이 쓰이지 않는다.
5. 한쪽 환경 변수 누락 시 다른 쪽이 정상 동작한다.
6. 탭별 캐시가 분리되고, 전환·새로고침·모달·검색어 처리가 아래 edge case 표대로 동작한다.
7. 브라우저 번들·응답에 두 서버 주소·토큰·이메일이 없다.
8. `pnpm lint`, `pnpm type-check`, `pnpm test`, `pnpm build` 통과, 죽은 코드 없음.

### I-01 건수 줄 문구

- 건수 줄은 서버 이름 없이 "전체 N개", 검색 중이면 "검색 결과 N개 / 전체 N개"로 표시한다. 숫자는 기존처럼 천 단위 구분(`ko-KR`)을 쓴다.

- 원천 우선순위: 1) 현재 서버 데이터(조회된 전체 목록)에 이미 있는 (국가코드, 국가명) 쌍, 2) 위에 없는 ISO alpha-3 표 항목은 `Intl` 한국어 이름, 3) alpha-3 표에 없는 코드(`HKR`, `ZYC`)는 선택 목록에서 제외한다. 이는 권장안이며 사용자 결정 N-1에서 확정한다.
- 수용 기준
  - 기존 도시가 있는 국가는 기존 데이터의 국가명 표기(예: KOR -> 한국)로 보인다. `Intl` 이름이 달라도 기존 표기가 우선한다.
  - 기존 데이터에 없는 국가도 `Intl` 이름으로 선택 가능하다.
  - 같은 코드가 서로 다른 국가명으로 기존 데이터에 있으면 최빈 표기를 쓴다(동률이면 먼저 나온 값). 이 경우 사용자 경고는 하지 않는다.
  - 새 라이브러리를 추가하지 않는다.
- Edge case: `Intl`이 한국어 이름을 못 주는 코드(코드 문자열 그대로 반환)는 목록에서 제외하거나 코드로 표시한다(디자인 단계 결정, 입력 가능 여부는 변하지 않는다).

### I-03 국가 검색 선택

- 입력칸에 국가명 또는 alpha-3 코드 일부를 입력하면 일치하는 국가 후보가 나오고, 하나를 고르면 국가코드가 자동 입력된다.
- 수용 기준
  - 한국어 국가명 부분 일치로 후보가 줄어든다. alpha-3 코드(대소문자 무시)로도 찾을 수 있다.
  - 후보를 고르면 `countryCode`가 대문자 alpha-3으로 채워지고 폼 검증이 통과한다.
  - 후보를 고르지 않은 채 임의 텍스트는 국가로 확정되지 않는다. 국가 미선택 상태로 저장할 수 없다.
  - 키보드(방향키·Enter·Esc)로 조작할 수 있고, 목록은 스크린 리더가 인식하는 역할(combobox/listbox 계열)을 가진다.
  - 수정 모드: 기존 도시의 국가코드가 목록에 있으면 선택된 상태로 열린다. 목록에 없는 코드(`HKR`, `ZYC` 등)인 도시는 N-1 결정에 따라 처리한다(권장: 기존 값을 그대로 표시하고 저장 가능, 새로 선택은 불가).
- 구현 제약: `src/components/common/`에 선택 컴포넌트가 없으면 Radix UI primitive로 구현 가능한지 먼저 확인한다(project.md 스타일 규칙).

### I-04 국가명 칸

- 국가를 선택하면 국가명이 선택 항목의 국가명으로 정해진다. 별도 자유 입력칸을 둘지, 선택 입력 하나로 합칠지는 N-2에서 확정한다.
- 수용 기준(권장안 기준: 국가 선택이 국가명과 국가코드를 함께 채우고 별도 국가명 입력칸을 없앤다)
  - 요청 본문의 `countryName`, `countryCode`는 선택한 항목의 값으로 채워져 기존 Route Handler 검증을 그대로 통과한다.
  - 수정 모드에서 기존 국가명이 선택 목록의 국가명과 다르면(예: 오래된 표기) 사용자가 국가를 다시 고르기 전까지 기존 값을 유지한다.

### I-05 위치 검색 엔드포인트

- 브라우저는 Nominatim을 직접 호출하지 않는다. 새 내부 Route Handler가 Nominatim을 호출하고 후보 목록(표시명, 위도, 경도, 후보 국가코드, 유형)만 반환한다. 서버 전용 모듈(`src/lib/server/`)에서 호출한다.
- 이 엔드포인트는 도시 API(`/api/cities*`)가 아니므로 2차의 `server` 쿼리는 요구하지 않는다(대상 서버와 무관). 세션 검증은 필수다(`withSession`).
- 수용 기준
  - 세션이 없으면 Nominatim 호출 없이 거부된다.
  - 입력은 도시명(필수, 공백 제거 후 비어 있으면 400)과 국가 alpha-3 코드(필수, 형식 검증)다. 알 수 없는 입력은 외부로 전달하지 않는다.
  - 호출 URL의 호스트는 고정이며 클라이언트가 호스트·경로를 지정할 수 없다. 응답 후보 수는 상한(권장 5개)을 둔다.
  - 요청에 식별 가능한 User-Agent를 붙인다. 값(연락처 포함 가능)은 환경 변수로 받을 수 있으며 코드·문서에 실제 이메일을 적지 않는다.
  - Nominatim 응답을 그대로 노출하지 않고 위 필드만 반환한다. 위·경도는 숫자(범위 -90~90, -180~180)로 검증하고 범위 밖 후보는 버린다.
  - 사용자 응답은 한국어 후보명(`accept-language=ko`)을 우선한다.

### I-06 "위치 찾기" 버튼과 후보 선택

- 모달에 "위치 찾기" 버튼을 둔다. 클릭할 때만 검색하며 입력 중 자동 호출(자동완성)은 하지 않는다.
- 수용 기준
  - 도시명과 국가가 모두 입력(선택)돼야 버튼이 활성화된다. 비활성 사유는 안내한다.
  - 클릭하면 로딩을 표시하고 중복 클릭은 막는다.
  - 후보가 1건 이상이면 목록(표시명 + 위·경도)을 보여 주고, 하나를 고르면 위도·경도 칸이 채워진다. 후보 자동 확정은 하지 않는다(1건이어도 사용자가 선택).
  - 채워진 위·경도는 이후 수정할 수 있고, 기존 숫자 검증을 따른다.
  - 수정 모드에서도 같은 버튼을 쓸 수 있다. 기존 좌표는 사용자가 후보를 고르기 전까지 바뀌지 않는다.
  - 위치 찾기 없이 수동으로 위·경도를 입력해 저장하는 흐름은 계속 가능하다.

### I-07 실패·0건·타임아웃·국가 불일치

- 위치 검색이 어떤 이유로 실패해도 폼 입력값과 수동 입력 흐름은 영향받지 않는다.
- 수용 기준
  - 네트워크 오류·Nominatim 4xx/5xx·응답 형식 오류·타임아웃은 각각 구분하지 않고 "위치를 찾지 못했습니다. 잠시 후 다시 시도하거나 위도·경도를 직접 입력해주세요." 계열의 사용자 문구로 표시한다(최종 문구는 `cityErrorMessage.ts`에 통일, 오류 원인별 문구를 컴포넌트에 흩지 않는다).
  - 0건: "검색 결과가 없습니다. 도시명을 확인하거나 위도·경도를 직접 입력해주세요." 계열 문구로 구분해 표시한다.
  - 서버 측 호출 타임아웃(권장 값은 설계 단계에서 결정)을 둔다. 타임아웃 시 상류 연결을 닫고 위 실패 문구를 보인다.
  - 429(요청 과다)는 일반 실패와 같은 문구로 처리하되, 연속 호출 방지는 I-08이 담당한다.
  - 후보의 국가가 선택한 국가와 다른 경우의 처리는 N-3에서 확정한다.
  - 상류 오류의 원문·URL을 사용자에게 노출하지 않는다.

### I-08 이용 정책 준수

- 일반 지식 기준 이용 정책: 초당 1회 이하, 식별 가능한 User-Agent, 자동완성 금지, 대량 조회 금지. 정책 원문은 구현 단계에서 확인한다(3-7 Q-1).
- 수용 기준
  - 위치 검색은 사용자 버튼 클릭에서만 시작된다(입력 이벤트·마운트·포커스에서 호출하지 않는다).
  - 서버는 연속 호출을 초당 1회 이하로 제한한다. 제한 방식(인스턴스별 시간 간격 기록 vs 클라이언트 쿨다운)은 설계 결정이나, 서버리스 다중 인스턴스에서는 서버 측 제한만으로 전역 1회/초를 보장하지 못하므로 이 한계를 문서에 적는다(Q-3).
  - 같은 입력(도시명+국가)의 재조회는 결과를 재사용해 불필요한 호출을 줄일 수 있다(권장, 필수 아님).
  - 클라이언트에서 버튼 클릭 직후 일정 시간(권장 1초) 재클릭을 막는다.
  - 이 도구는 내부 전용 어드민이므로 대량 일괄 위치 조회 기능은 만들지 않는다.

### I-09 문서·테스트

- `src/docs/city-api-reference.md`에 위치 검색 내부 엔드포인트 계약(입력·출력·오류)을 추가한다. User-Agent용 환경 변수를 도입하면 `.env.example`에 placeholder로만 추가하고 `project.md`는 필요한 경우에만 갱신한다.
- 테스트: 건수 줄 문구, 국가 목록 합성 규칙(기존 쌍 우선, 비표준 코드 제외), 국가 선택 후 폼 값, 위치 검색 Route Handler(세션 없음 거부, 입력 검증, 0건, 상류 오류·타임아웃, 필드 정제), 후보 선택 후 위·경도 반영. 테스트 제목 설명은 한글. 외부 Nominatim을 호출하는 테스트는 만들지 않는다(fetch 모킹).

## 3-3. 전체 수용 기준 (완료 기준)

- 건수 줄에 서버 이름이 없고 I-01 문구 형태를 따른다.
- 도시 추가·수정 모달에서 국가를 검색해 고르면 alpha-3 코드가 자동 입력되고, 기존 데이터의 국가명 표기가 우선한다.
- "위치 찾기" 클릭으로 후보를 받아 하나를 고르면 위도·경도가 채워지고, 수정 가능하며, 수동 입력 흐름도 유지된다.
- 위치 검색은 클릭 때만 호출되고, 세션 없이는 외부 호출이 없으며, 브라우저가 Nominatim을 직접 호출하지 않는다.
- 실패·0건·타임아웃·국가 불일치에서 사용자에게 한국어 안내가 나오고 폼 입력값은 보존된다.
- 새 npm 라이브러리를 추가하지 않는다.
- `pnpm lint`, `pnpm type-check`, `pnpm test`, `pnpm build`가 통과한다.

## 3-4. Edge case 정리

| 상황 | 기대 동작 |
| --- | --- |
| 도시명이 비어 있거나 공백뿐 | 위치 찾기 버튼 비활성, 서버도 400 |
| 국가 미선택 | 위치 찾기 버튼 비활성(국가 필터 없는 전 세계 검색은 하지 않음) |
| 후보가 선택한 국가와 다른 국가 | N-3 결정에 따라 처리 |
| 0건 | 0건 전용 문구, 좌표 칸 불변 |
| Nominatim 타임아웃·5xx·429·네트워크 오류 | 실패 문구, 좌표 칸 불변, 재시도 가능 |
| 응답 필드 누락·숫자 아님·범위 밖 | 해당 후보를 버린다. 모두 버려지면 실패(형식 오류)로 취급 |
| 동명 도시 다수(예: 같은 국가 내 여러 곳) | 후보 목록에 모두 표시(상한 내), 사용자가 선택 |
| 후보 선택 후 사용자가 좌표 직접 수정 | 수정값 유지, 재검색 전에는 덮어쓰지 않음 |
| 위치 찾기 후 도시명 또는 국가 변경 | 이전 후보 목록은 비운다(오래된 후보로 좌표 입력 방지) |
| 모달 닫힘·저장 중 진행 중이던 검색 응답 도착 | 응답을 무시한다(닫힌 모달·다른 값에 반영 금지) |
| 수정 모드에서 국가코드가 목록에 없음(`HKR`, `ZYC`) | N-1에 따라 기존 값 유지 |
| 기존 데이터 국가명이 `Intl` 이름과 다름 | 기존 데이터 표기를 선택 목록 이름으로 사용 |
| 검색어 입력 직후 빠른 연타 | 중복 요청 없음(로딩 중 비활성 + 재클릭 간격) |
| 세션 만료 | 기존 세션 만료 처리(401 처리 흐름)를 따른다 |
| 건수 줄 검색 결과 0건 | 기존 동작 유지(서버 이름만 제거) |

## 3-5. 비기능 요구사항

- 보안: 위치 검색 엔드포인트는 세션 필수, 입력 검증, 고정 호스트(SSRF 방지), 상류 원문·내부 URL 비노출. User-Agent 값 등 설정은 서버 환경 변수로만 다루고 `"use client"` 파일에서 import하지 않는다.
- 성능: 위치 검색은 클릭당 1회 외부 호출. 타임아웃을 둬 UI가 무한 로딩하지 않는다. 국가 목록은 클라이언트에서 한 번 합성해 재사용하며 목록 전체 재조회를 추가하지 않는다.
- 접근성: 국가 선택은 키보드 조작·스크린 리더 역할 지원, 후보 목록 선택은 키보드로 가능, 로딩·오류 문구는 보조기기에 전달(`aria-live` 등). 오류는 색에만 의존하지 않는다.
- 호환: 데스크톱 우선(최소 1024px). 기존 디자인·브레이크포인트·애니메이션 유지. `Intl.DisplayNames` 지원 범위는 최신 데스크톱 브라우저 기준(일반 지식, 미확인).
- 규칙: 서비스 -> 훅 -> 컴포넌트 계층, `queryKeys`/`queryOptions` 규칙을 따른다(위치 검색은 사용자 액션이므로 mutation 형태 여부는 설계 결정). 사용자 문구는 `cityErrorMessage.ts`로 통일.

## 3-6. 범위 밖 (사용자가 요청하지 않음)

- 입력 중 자동완성형 위치 검색, 대량·일괄 좌표 조회
- 지도 위 핀 선택 UI
- 국가 선택 목록의 새 라이브러리 도입, 국기 표시 추가
- 좌표로 도시명·국가를 역으로 채우는 역지오코딩
- 건수 줄 외 문구(로딩·빈 목록·검색 결과 없음·토스트·오류)의 "서버" 표기 변경
- 운영 서버 쓰기 허용, 기존 도시 데이터의 일괄 정정(예: `HKR`, `ZYC` 수정)
- 유료·키가 필요한 지오코딩 서비스로의 전환

## 3-8. 사용자 결정이 필요한 항목

| # | 질문 | 권장안 | 이유 |

| N-1 | 국가 목록 원천과 비표준 코드(`HKR`, `ZYC`) 처리 | 기존 서버 데이터의 (코드, 국가명) 쌍을 우선하고, 없는 국가는 alpha-3 표 + `Intl` 한국어 이름으로 보충한다. `HKR`·`ZYC`는 새 선택 목록에는 넣지 않고, 이 코드를 가진 기존 도시를 수정할 때는 기존 값을 그대로 보여 주고 저장을 허용한다 | `Intl` 이름만 쓰면 11개국 표기가 기존 데이터와 갈라진다. 비표준 코드를 새 입력에 노출하면 오류 데이터가 늘어난다. 기존 도시 수정을 막으면 다른 필드도 못 고친다 |

## 3-9. 사용자 결정 확정 (2026-11-09, T02 승인)

| ID | 결정 | 3-8 권장안과의 차이 |
| --- | --- | --- |
| N-1 | 국가 선택 목록은 alpha-3 표 + 브라우저 `Intl` 한국어 국가명만 쓴다. 기존 서버 데이터의 국가명은 목록 원천으로 쓰지 않는다 | 권장안과 다름. 사용자는 아래 영향을 안내받고 선택했다: 11개국(예: KOR 한국→대한민국)은 새로 추가하거나 수정 후 저장하면 국가명이 `Intl` 이름으로 바뀐다. `HKR`·`ZYC`는 목록에 없으므로 이 코드를 가진 도시를 수정하려면 목록의 국가를 다시 골라야 한다(기존 값 유지 저장 없음) |
| N-2 | 국가명은 국가 선택으로 자동 채우고 직접 수정할 수 없다(별도 입력칸 없음) | 권장안과 같음 |
